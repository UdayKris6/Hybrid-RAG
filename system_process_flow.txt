================================================================================
HYBRID RAG DUPLICATE IDEA CHECKER - SYSTEM PROCESS FLOW & OPTIMIZATIONS
================================================================================
Target Audience: Peer Developers / Technical Demo

This document outlines the end-to-end technical pipelines, collection architectures, 
scoring formulas, and specific performance optimizations implemented in the 
Hybrid RAG Duplicate Idea Search & Scanning System.

--------------------------------------------------------------------------------
1. SYSTEM ARCHITECTURE & DATA BOOTSTRAP
--------------------------------------------------------------------------------
* DATABASE ENGINE: Qdrant in local-file storage mode (path="./qdrant_storage").
* DUAL-COLLECTION LAYOUT:
  a. "ideas" (Parent collection):
     - Vectors: "title" (dense vector, e.g., 3072 dims for Gemini, 1536 for OpenAI)
     - Sparse Vectors: "lexical" (32-bit hashed sparse weights for BM25 term matching)
     - Payload: Full title, description, summary, vertical_domains, horizontal_technologies, topics, and tags.
  b. "idea_chunks" (Child collection):
     - Vectors: "description" (dense vector, matching size of parent vector config)
     - Payload: parent_id, parent_title, parent_description, chunk_text, chunk_index, and parent_topics.
* COLD BOOT INITIALIZATION:
  - On FastAPI startup, init_db() checks Qdrant collections.
  - Generates BM25Vectorizer state by scrolling all records in Qdrant, computing 
    corpus document frequencies (DF), and fitting corpus average length parameters.
  - Pre-loads local Cross-Encoder reranker ('cross-encoder/ms-marco-MiniLM-L-6-v2') 
    in memory to eliminate first-request lag.

--------------------------------------------------------------------------------
2. IDEA CREATION PIPELINE (SAVE & INDEX)
--------------------------------------------------------------------------------
When a user indexes a new idea (e.g. "Smart AI-powered Grocery List Planner"), the 
following asynchronous stages run:

   [Client Angular Form Submit]
               |
               v
  [1. LLM Structured Metadata Extraction]
        - Prompts Gemini-3.1-flash-lite / GPT-4o-mini to extract a JSON schema:
          * "vertical_domains": Target industries (e.g., ["HealthTech", "E-commerce"])
          * "horizontal_technologies": Technical platforms (e.g., ["AI/ML", "Mobile App"])
          * "summary": Concise 2-sentence value proposition
          * "tags": Specific keywords/features
        - Combines verticals + horizontals into a "topics" list for backward compatibility.
               |
               v
  [2. Dense Vector Generation]
        - Generates dense vectors using active provider (Gemini embedding-2 or OpenAI text-embedding-3-small).
        - Generates:
          * title_vector = embed(title)
          * description_vector = embed(description)
               |
               v
  [3. Hashed BM25 Sparse Vectorizer]
        - Concatenates Title + Description to make lexical text.
        - Splits text into lowercase word tokens.
        - Maps each token to a deterministic 32-bit index (MD5-hashed modulo 2^32 - 1).
        - Computes weights using the BM25 formula:
          Weight = smoothed_idf(t) * tf_normalized(t, doc_len)
               |
               v
  [4. Parent Upsert in Qdrant]
        - Writes parent PointStruct into "ideas" collection containing title vector, 
          sparse lexical vector, and payload metadata (domains, techs, summary, tags).
               |
               v
  [5. Parent-Child Chunking & Child Upsert]
        - Splits descriptions longer than 1000 characters into passages of 
          max 800 characters with 150 characters of overlap.
        - Generates dense embeddings for each description chunk.
        - Generates deterministic child UUIDs: uuid5(namespace_dns, f"idea_{parent_id}_chunk_{idx}").
        - Upserts all chunk points into "idea_chunks" child collection.

--------------------------------------------------------------------------------
3. DUPLICATE IDEA CHECKING PIPELINE (SEARCH & RERANK)
--------------------------------------------------------------------------------
When a user types a draft query and clicks "Scan for Similarities", the system 
searches the database *without* saving:

   [Draft Query submitted via POST /api/ideas/check]
                       |
                       v
    [1. Embed Query Title & Description (Dense)]
                       |
                       +-------------------------------------------------+
                       |                                                 |
                       v (Search 1)                                      v (Search 2)
           [Qdrant Title Search]                            [Qdrant Description Chunk Search]
             - Match query title vector                        - Match description vector 
               against parent "ideas"                            against child "idea_chunks"
             - Limit: top_k=15                                 - Limit: top_k=45
                       |                                                 |
                       |                                                 v
                       |                                     [Grouping/Max-Pooling]
                       |                                       - Group chunk hits by parent_id
                       |                                       - Keep only the chunk with the 
                       |                                         highest cosine score per parent
                       |                                       - Truncate to top_k=15 parent matches
                       |                                                 |
                       +-----------------------+-------------------------+
                                               |
                                               v (Search 3)
                                   [Qdrant Sparse Lexical Search]
                                     - Compute sparse vector for query tokens (TF only)
                                     - Search parent "lexical" index in "ideas"
                                     - Limit: top_k=15
                                               |
                                               v
                                [2. Reciprocal Rank Fusion (RRF)]
                                  - Merge candidates from Title, Grouped Description, 
                                    and Sparse lists.
                                  - For each candidate d, compute RRF score:
                                    RRF_Score(d) = sum( 1 / (60 + Rank_in_List) )
                                  - Sort candidates by RRF_Score descending.
                                  - Truncate to top 15 candidates.
                                               |
                                               v
                            [3. LLM Metadata Extraction on Query Draft]
                              - Call LLM to retrieve the query's vertical_domains 
                                and horizontal_technologies.
                                               |
                                               v
                                [4. Cross-Encoder Local Rerank]
                                  - For each candidate, format input:
                                    "Categories: {topics}. Title: {t}. Description: {d}"
                                  - Evaluate pairs on CPU using Cross-Encoder model.
                                  - Convert output logits to probabilities via sigmoid:
                                    sigmoid_score = 1.0 / (1.0 + exp(-logit))
                                               |
                                               v
                             [5. Dynamic Category Overlap Penalty]
                               - Extract query vertical domains & candidate verticals.
                               - Compare vertical domain sets directly.
                               - If zero core domain overlap is present:
                                 sigmoid_score = sigmoid_score * 0.70 (30% reduction)
                               - Round to 4 decimal places.
                                               |
                                               v
                                [6. Warning Threshold Assessment]
                                  - If max(similarity_score) >= 0.82:
                                    * Flag is_duplicate = True
                                  - Return ranked candidates and duplicates status JSON.

--------------------------------------------------------------------------------
4. KEY IMPLEMENTED OPTIMIZATIONS & VERIFICATION METRICS
--------------------------------------------------------------------------------

A. BM25 Sparse Vectorizer vs. Simple Term Frequency (TF)
   - *Problem:* Simple TF hashing weights generic connecting words (a, to, the) equally, 
     polluting search rankings.
   - *Solution:* Implemented a stateful BM25Vectorizer that tracks inverse document 
     frequencies (IDF) and normalized lengths.
   - *Metric:* Upgraded lexical search contrast ratio (1st vs 2nd candidate) by **28.5%** 
     (Simple TF contrast ratio: 1.077 vs. BM25 contrast ratio: 1.384).

B. Parent-Child Chunking
   - *Problem:* Matching full descriptions directly in vector space dilutes specific 
     feature nuances on long descriptions (>2,000 chars).
   - *Solution:* Child chunks are searched individually. The best matching section 
     is max-pooled and mapped back to the parent, giving higher retrieval precision.

C. Structured LLM Domain Extraction
   - *Problem:* Shared horizontal technologies (e.g. "Blockchain", "AI") cause 
     Cross-Encoders to report false-positive duplicates across distinct industries 
     (e.g., Blockchain Bank Ledger vs. Blockchain Medical Ledger). Pre-defined static 
     lists are hard to maintain.
   - *Solution:* The LLM separates industries (vertical domains) and technical enablers 
     (horizontal technologies) at extraction time. Zero-overlap penalties are computed 
     dynamically specifically on vertical domain matches.
   - *Metric (Case 1 Benchmark):*
     * Baseline Similarity:        **98.55%** (False Duplicate Warning)
     * Context-Engineered Score:   **99.77%** (False Duplicate Warning)
     * Final Penalized Score:      **69.84%** (Correctly Identified as OK / Unique Concept)

D. Local Cross-Encoder Reranker (MiniLM)
   - Performs joint attention over query-document texts simultaneously.
   - Run in-process on CPU, resolving heavy dependencies on cloud API limits (like Cohere).
   - Serves as the ultimate verification layer for Reciprocal Rank Fusion outputs.

Metadata Extraction (gemini-2.5-flash) Uses Gemini to analyze the new idea and return a JSON containing a 2-sentence summary, 1-3 broad topics, and 3-6 specific technology tags.

Dense Vector Embeddings (gemini-embedding-2) Generates a high-dimensional (3072-dimensional) vector representing the semantic meaning of the draft's title and description separately.

Sparse Vector Generation (Local Deterministic Hash) Builds a BM25-style lexical vector in Python by hashing words to represent exact keyword frequency weights for word-matching.

Multi-Vector Hybrid Search (Qdrant Database) Queries Qdrant to find candidates using three indexes: dense Title similarity, dense Description similarity, and sparse lexical matching.

Reciprocal Rank Fusion / RRF (FastAPI backend) Merges the three separate search result rankings into one unified list, balancing keyword matches and conceptual matches fairly.

Cross-Encoder Reranking (ms-marco-MiniLM-L-6-v2) A local, lightweight transformer model that evaluates the semantic context of candidate pairs to output a final similarity percentage.

Options:
1. Alternatives for Dense Encoding (Embeddings)
Currently, we use Gemini's gemini-embedding-2 (3,072 dims) over the network.

Option A: BGE-M3 (BAAI/bge-m3) — Best Open-Source Multilingual Model
The Concept: A state-of-the-art model from BAAI that outputs dense vectors, sparse tokens, and multi-vectors simultaneously in one forward pass.
Pros: Runs completely locally/offline (no API keys, no 503 rate limits), performs phenomenally well on the global MTEB benchmark, and natively supports multi-vector late interaction.
Cons: Takes up ~560MB and takes about 20–50ms to run on CPU.
Option B: GTE-Small (Alibaba-NLP/gte-small) — Best for CPU Speed
The Concept: A highly compact, optimized embedding model.
Pros: Tiny size (~120MB), extremely fast execution (under 5ms on CPU), and outputs a smaller 384-dimensional vector, which makes Qdrant index searches much faster.
Cons: Slightly lower retrieval performance on complex, paragraph-long queries.
2. Alternatives for Reranking
Currently, we use the local ms-marco-MiniLM-L-6-v2 (~80MB).

Option A: BGE-Reranker-Base (BAAI/bge-reranker-base) — High-Accuracy Upgrade
The Concept: A larger, more modern reranking transformer.
Pros: Significantly higher NDCG scores on search benchmarks. It does a better job of understanding complex negative matches.
Cons: Size is 270MB, which increases startup memory and doubles CPU inference latency (~40ms per candidate).
Option B: Cohere Rerank V3 (Cloud API) — Industry Leader
The Concept: A commercial, cloud-based reranker.
Pros: The highest-performing reranker on the market. Handles multiple languages, spelling errors, and complex technical jargon effortlessly.
Cons: Requires a paid API key and adds ~100ms of network latency.
